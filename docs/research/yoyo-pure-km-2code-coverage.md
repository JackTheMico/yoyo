# 调研报告：在不新增重码的前提下，让更多常用字「一次并击」打出

> **状态**：研究完成 · 2026-10-26
> **问题**：`yoyo-pure-km` 前 1500 常用字里有 179 个只能打三码（2 击）。能否在**不增加任何重码**的前提下，让其中更多的字变成「两码 / 一次并击」？
> **方法**：以真实词表 `rime/yoyo-pure.dict.yaml`（单字 6640 / 词 10 万+）、字频源 `rime/yoyo-yx-char.dict.yaml`、运行时映射 `rime/lua/yoyo/data/pure_dict_map.lua` 做码位台账；把「不新增重码」形式化为「每个 XY 码位挂的 text 数不增加」，再用二分匹配求解最大覆盖，并对挤词成本做参数扫描。
> **结论先行**：**严格意义的「2 键两码」空间已经饱和，且卡点不是空位而是「前两根」这条助记规则** —— 2581 个前缀位要对 6400 个三码字。因此「再加二简」在 XY 空间里最多只能再救 10 个字（免费）到 102 个字（吃掉全部 100 个空位、其中 84 个得死记）。
> **真正的杠杆在 `%` 空格并击命名空间**：那里还有 2724 个空位、同样是「一次并击上屏」，可以把 179 个缺口**全部**补上（93 个连助记都保持「前两根」），代价仅是挤掉 15 个低频词位、词频合计 7.4 万。

---

## 1. 事实基线（全部实测，可复现）

### 1.1 XY 码位台账

| 项 | 数值 | 说明 |
|---|---|---|
| XY 码位理论容量 | 3600 | 左手 60 码元 × 右手 60 码元 |
| 已被单字占用 | 2712 | 其中 2655 个位同时挂了一个词（双候选） |
| 仅被词占用 | 788 | 单字可以「挤词」进来 |
| **空闲** | **100** | 唯一真正无人使用的资源 |
| 挂 2 个单字的码位 | **0** | 「单字零重码」在 XY 空间成立 |

`_X` / `+X` 一简 120 个位**全部**是「1 字 + 1 词」双候选，无空位、无冗余。

### 1.2 单字 2 码 = 全码前两根（零例外）

同时拥有 3 码全码与 2 码简码的单字共 **2472** 个，**2472/2472** 都满足 `2码 == 3码[:2]`（如 `等: cVz → cV`、`但: awf → aw`）。没有一个例外。

这条规则决定了一件关键的事：**一个 3 根字只有 6 个「形状可推导」的两码候选** —— 从 3 个码元里取 2 个（C(3,2)=3 种）× 左右手谁在前（2 种）。为什么可以换手：`chord_utils` 实测左右手各自都能产出**全部 60 个码元**（`research/probe_dau_hands.py`），所以 `XY` 与 `YX` 是两个互不冲突的合法 chord。

### 1.3 结构性瓶颈：前缀不够分

| 项 | 数值 |
|---|---|
| 3 码前缀（前两根）去重数 | **2581** |
| 需要 2 码的三码字 | **6400** |
| 平均竞争 | **2.48 字争 1 个前缀位** |

这是 179 个缺口的根因：不是没有码位，而是**「前两根」这条助记规则把可用码位限制成了 2581 个**。

实测佐证：179 个缺口字的「前两根位」**100% 已被别的字占走**；用六解（异序/异取）去撞那 100 个空位，只有 **10 个**撞得上。所以「找出空位再填」这条路几乎无效。

### 1.4 现有分配已接近字频最优

对 1562 个「多字共用同一前缀」的组做「让位给组内字频最高者」的重排：共 56 处可动，但前 1500 的缺口只从 **179 → 177**（加权覆盖 96.73% → 96.79%）。

**结论：不要指望「重排」捡便宜**。现在的分配已经把每个前缀位给了该组最高频的成员（120 个一简字不再占用二简位，这层优化也已做到）。

## 2. 路线 X：严格「两键两码」（不带空格）

在「每码位 text 数不增加」约束下，单字只能进「空位」或「挤走一个词」。逐级求解结果（`research/solve_2code_plan.py`，含不变量断言）：

| 挤词上限 | 前1500 缺口 | 挤词数 | 词频损失 | 收益/成本 | 助记构成 |
|---|---|---|---|---|---|
| 0（只吃空位） | 179 → **77** | 0 | 0 | ∞ | 形状可推导 23 / 纯记忆 84 |
| ≤ 1,000 | → 28 | 49 | 23,888 | 3056 : 1 | — |
| **≤ 5,000** | → **0** | 77 | **82,686** | 943 : 1 | 形状可推导 36 / 纯记忆 143 |
| 不限 | → 0 | 77 | 3,592,292 | 22 : 1 | 形状可推导 62 / 纯记忆 117 |

两点解读：

1. **免费档（挤词上限 0）能白拿 102 个**，缺口降到 77，零词频损失 —— 但其中 84 个是「纯记忆位」（形状推不出来，只能背），只有 23 个能靠六解推出来。
2. **挤词上限 5000 就能清零**，损失 8.3 万词频（相对前 1500 字的 23.9 亿总频是 0.003%）。但助记仍差：143/179 是死记。
3. 「不限」为了多 26 个可推导位，把成本推到 359 万（43 倍）—— 不划算，因为代价是会挤掉 `点击`(97 万)、`有什么`(77 万) 这种真正常用的词。

**路线 X 的硬伤不是重码，是记忆**：XY 空间里能给的字都已经给了，剩下的位要么在别人的前缀组里，要么就得死记。

## 3. 路线 P：`%` 空格并击命名空间（推荐）

### 3.1 为什么 `%` 是同一个「一击」而不是多一击

`%XY` 的由来是 `chord_composer` 的「空格并击」：左手按 X 的键、右手按 Y 的键、**同时**有一根拇指压住空格，一次 chord 输出 `%`→`X`→`Y` 三个字符。空格是并击的一部分，**不是额外的击**。项目自己的口径也是这么算的（`research/yoyo-pure-km-one-stroke-count.md`：995 个 % 简词记为「一击上屏」）。

### 3.2 空间与现状

| 项 | 数值 |
|---|---|
| `%` 空间总容量 | 3720（`%XY` 3600 + `%_X` 60 + `%+X` 60） |
| 已占用（`space_brief_map`） | 996 |
| **空闲** | **2724** |

### 3.3 关键判断：单字能不能挂 `%` 码？

代码层面可以，三处依据：

1. `rime/lua/yoyo/pure_popping.lua:137-159`（Pattern S）：只要 `input` 以 `%` 开头，就取 `space_brief_map[input .. incoming]` 命中即 `commit_text` + `kAccepted`。**全程没有任何 text 长度判断**，单字与词走同一条路。
2. `rime/scripts/generate_pure_dict_map.py:51-54`：`if raw_code.startswith("%") and len(raw_code)==3: space_brief_map.setdefault(...)`。**只校验码长 3，不校验 text 长度**，单字条目会被正常收进映射表。
3. 同一处 `continue` 保证 `%` 码**不进入** `dict_map` / `chars_3code` / `words_4code` —— 因此不会污染一简顶屏、3 码判定、4 码词判定这些状态机。

> ⚠️ **置信度**：以上是代码层面的确证。**端到端实机尚未验证**（见第 7 节）。

### 3.4 求解结果：179 → 0

按「优先用空闲 % 位；都不行才挤一个低频词位」贪心求解（`research/final_numbers.py`）：

| 项 | 数值 |
|---|---|
| 补上的字 | **179 / 179** |
| 直接占空闲 `%` 位 | 164 |
| 挤占已有词位 | 15（词频合计 **74,163**） |
| `%` 空间占用 | 996 → 1160，剩余 **2560** |
| 助记：`%前两根` | **93（52%）** |
| 助记：六解（异序/异取） | 86 |
| 收益/成本 | ≈ **1050 : 1**（收益 77,940,128 / 成本 74,163） |

被挤的 15 个词位（全部是低频词）：

```
%fj ← 一定(58,692)      %ba ← 中华人民共和国(3,113)   %wb ← 是啊(2,863)
%bb ← 呕吐(2,099)       %an ← 依法(1,966)              %iC ← 提速(1,329)
%dn ← 泉水(835)         %wg ← 暗暗(814)                %rY ← 人际(678)
%gr ← 很热(649)         %bz ← 哪来(409)                %jf ← 实事(356)
%bc ← 哪管(178)         %ez ← 乡镇企业(101)            %;f ← 剥削阶级(81)
```

`%fj ← 一定` 是唯一的异类（5.9 万词频）：宣 的 6 个形状候选位全被占了。若不愿动 `一定`，给「宣」随便指一个剩余空位当死记码即可 —— 这类取舍只有 1~3 个字。

### 3.5 举例

| 字 | 全码（3 码，2 击） | 新增码（1 击） | 助记 |
|---|---|---|---|
| 少 | `Etp` | `%Et`（空格并击） | 前两根 + 空格 |
| 总 | `Xb:` | `%Xb` | 前两根 + 空格 |
| 型 | `fpV` | `%fp` | 前两根 + 空格 |
| 听 | `b/j` | `%b/` | 前两根 + 空格 |
| 选 | `mJp` | `%Jm` | 次根+首根 反手序 + 空格 |
| 副 | `fbW` | `%fW` | 首根+末根 + 空格 |

注意 `%Et` 与「某个字的二简 `Et`」**不冲突**（`Et` 现在是「省」的二简），二者是不同握手势。

## 4. 两条路线对比

| | 路线 X（严格两码） | 路线 P（`%` 空格并击） |
|---|---|---|
| 码形 | `XY`（2 键） | `%XY`（2 码元 + 空格，同一次 chord） |
| 缺口清零 | 需要挤 77 个词位 | 需要挤 15 个词位 |
| 词频损失 | 82,686 | 74,163 |
| 助记可推导占比 | 20%（36/179） | **100%**（93 前两根 + 86 六解） |
| 空间余量 | 0（100 空位用光，再要就得抢词位） | 2560 |
| 运行时风险 | 零（纯数据重排） | 低但需实机回归 |
| 观念一致 | 破坏「前两根」助记，方案卖点受损 | 「前两根 + 空格」是新规则，但规则简单且可教 |

**推荐路线 P**。它同时解决了空间、助记、成本三个问题；路线 X 只能解决空间（还要牺牲助记）。

**保守备选**：先做路线 X 的免费档（只吃 100 个空位，缺口 179→77，零成本零风险），把 P 挂在实机验证后上线。

## 5. 落地改动（路线 P）

纯数据改动，**不需要改 schema**：

1. 在 `rime/yoyo-user.dict.yaml` 追加 179 行单字 `%` 码，例如
   ```
   少	%Et	0
   总	%Xb	0
   ```
   （`%` 码条目权重写 0；`space_brief_map` 只用「码 → text」，不读权重。）
2. 跑 `rime/scripts/generate_pure_dict_map.py` 重生成 `rime/lua/yoyo/data/pure_dict_map.lua`。
   校验：新表条目数应从 996 变为 1160 左右，并含 `["%Et"] = "少"`。
3. **不新增任何重码校验**：每个 `%` 位只挂 1 个 text（要么原本空着，要么原本的词已删）。可用
   `research/solve_2code_plan.py` 尾部的断言口径复核。
4. 部署 + 实机回归（见第 7 节）。

生成规则可沉淀到 `gen_brief_words.py` 的同一管线里（它已经是「写 yoyo-user.dict.yaml → 重生成 lua」这套流程），加一个「单字溢出段」即可，避免下一次手工维护。

## 6. 收益的真实口径（别高估）

77.9M 击是「这 179 个字每次以**单字**形式被输入」时节省的总量。按 `docs/research/yoyo-pure-km-code-length-reduction.md` 的测算，最优分词下词命中率 90.9%，这 179 个字绝大多数出现时都在词里（如「少」多在「多少」「少数」中）。所以：

- **真实日常收益明显小于 77.9M**，收益主要落在「单字输入」场景（人名、单字词、词库未命中的回落）。
- 但对「单个常用字打起来别扭」的体感改善是直接的 —— 这正是本问题的出发点。

## 7. 未确认项与风险

1. **端到端实机未验证（主要未确认项）**。
   我为这件事搭了独立 librime 探针（`research/probe_pct_v3.c`，隔离副本 + 手工 dlopen `librime-lua.so` + 注入字面量 `%Et`）。结果：lua 插件能加载（日志确认 `loading plugin 'lua'`、`registering component: lua_processor`），但**整条 popping 链路在独立进程里跑不起来** —— 连已知应成立的对照 `_d` + `b` → 的 都不弹。因此这个探针**不能**用来确认或否认 `%Et`。
   进一步排查方向：`chord_composer` 只认 press+release 成对事件，而 `rime_api::process_key` 只发单次按键；`pure_popping` 拿不到 chord 逐字符注入的时序，整条 FSM 退化。这与我此前记录的「chord_composer 键位层无法用 rime_api 驱动」一致。
   **必须在 fcitx5 真机上验证**：选 `yoyo-pure-km`，按 左 `E` 组 + 右 `t` 组 + 空格，确认一次并击上屏「少」。
2. **反查显示的连带影响**：`rime/scripts/generate_reverse_data.py:167-178` 把 `%` 码当作「简码」收录。给单字加 `%` 码后，反查（`` ` ``）里这些字会多显示一个 `%XY` 简码。属预期行为，但要确认显示不刺眼。
3. **`%` 空间是后续降码长的主要储备**：`code-length-reduction.md` 的 L1 建议把 995 补满到 3720。本方案只吃掉 164 个空位，剩下 2560 仍够用，但两件事要一起排期。
4. **字频口径**：本报告「常用字」= 按 `yoyo-yx-char.dict.yaml` 的 weight 排序（该 weight 实为「含该字的词频之和」，故「型/副/酱」这类偏高）。若换成《现代汉语常用字表》口径，179 这个数和具体字表会变，但结构性结论（2581 vs 6400、XY 满载、% 有 2724 空位）不变。
