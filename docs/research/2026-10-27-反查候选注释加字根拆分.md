# 拼音反查候选注释加「字根拆分」：可行性与落地

- 日期：2026-10-27
- 问题：拼音反查（`` ` `` + 全拼）时，能否在候选里显示字根拆分，让用户看到「这个字凭什么这么打」。
- 结论：**能，且已实现并验证**。覆盖 6640 个单字的 **96.9%**（6435 字）；剩余 3.1% 与「多字根字的第二根」是数据层面的硬边界，不是代码问题。

---

## 1. 结论速览

| 维度 | 结论 |
|---|---|
| 显示通道 | 唯一可用的是候选 `comment`。librime-lua 的 `Candidate` 有 comment 字段，fcitx5-rime 不截断；提示行（`reverse_lookup/tips`）与 `cand.preedit` 在 fcitx5-rime 不渲染 |
| 数据来源 | `elements.txt`（huma 导出，形码拆分单一真源）+ `mapping.yaml`（字根码表）+ README 取码规则 |
| 首码归属 | 反推字根大码后，**96.2%** 的单字首码能对齐到首根 |
| 逐码全对齐 | **27.4%**（双字根字，末根占两码）；**65.8%** 只能对齐首码与末码 |
| 覆盖率 | 6435 / 6640 字可显示拆分，其余 205 字（`无法归属` 182 + `单根不符` 13 等）退回纯编码 |
| 主要代价 | 候选注释变宽（约 8–12 字符/候选）；数据文件 196 KB（首次反查时懒加载） |

---

## 2. 为什么显示通道只能是 `comment`

三条都来自一手源码，本轮已复核：

1. **`Candidate` 是五参数构造**，`type` 在首位：
   `make(const string type, size_t start, size_t end, const string text, const string comment)`
   （`librime-lua/src/types.cc`，注册名 `"Candidate"`）。现有代码 `Candidate("yoyo", seg.start, seg._end, c[1], c[2])` 本来就符合，不需要改签名。
2. **可写字段**：`type / start / _start / _end / quality / text / comment / preedit`；**没有 `shadow` 字段**（只有 `ShadowCandidate(...)` 构造与 `:to_shadow_candidate()`）。
3. **`comment` 不被任何一层截断**：librime 的 `candidate.cc` 无长度处理；fcitx5-rime 的 `rimecandidate.cpp` 只做 `setComment(Text{candidate.comment})`，无 substr/elide。多宽由前端布局决定。

生态先例：`rime/rime-cangjie` 的 `cangjie5.schema.yaml` 正是把码位翻成字根塞进注释——

```yaml
reverse_lookup:
  comment_format:
    - "xlit|abcdefghijklmnopqrstuvwxyz|日月金木水火土竹戈十大中一弓人心手口尸廿山女田難卜符|"
```

**但这条路对本仓不可直接照搬**，两个原因：`comment_format` 只作用于 C++ translator（`translator_commons.cc` 加载、`reverse_lookup_translator.cc` 的 `Peek()` 里 Apply），而麓鸣的反查是 `lua_translator`，librime-lua 里根本没有 `comment_format` 的实现；且仓颉 24 个码元与字根一一对应，麓鸣是 ~60 个码元对 535 个字根（多对一），纯 `xlit` 无法还原具体字根。所以必须在 Lua 里按**逐字拆分数据**拼串。

## 3. 数据可行性：能对齐到什么粒度

### 3.1 取码规则决定了能算到哪一步

README「单字取码规则」：

- 单字根字：全码 = 该字根双编码（大码 + 小码）
- 双字根字：第一根大码 + 第二根大码 + 第二根小码
- 多字根字：第一根大码 + 第二根大码 + 最后一根大码

而 `elements.txt` 每字只导出 **首根 / 末根** 两个根（各带 `.0` 大码 / `.1` 小码 两个实例）。于是：

- **首码恒等于首根大码** → 总能归属；
- **双字根字**：末根占第 2、3 码 → 三码全可归属；
- **多字根字**：第 3 码 = 末根大码（可归属），第 2 码 = 第二根大码，**第二根的名字数据里没有** → 只能留空。

### 3.2 实测（脚本 `rime/scripts/gen_zigen_align.py`）

从 6399 个三码单字反推字根码元（沿用 `zigen_table/generate_yx_mapping.py` 的投票法，不迷信 `mapping.yaml`）：

- 首码 == 首根大码：**5620 / 5842 = 96.2%**
- 大码无分歧的字根 336 / 345；少数分歧是手别大小写（`艹` p/P、`火` ;/M）
- **`mapping.yaml` 有 22 个字根的小码与实际编码脱节**，例如 `辶` 记为 `pz`，真实取 `c`（这、进、达 全部是 `…pc`）。所以生成器一律走反推，只在反推不到时回退 `mapping.yaml`。

分类结果（6409 个有拆分的单字）：

| 形态 | 字数 | 占比 | 注释形态 |
|---|---:|---:|---|
| 多字根·首末对齐 | 4364 | 65.8% | `d.O 白d·丶O`（首根/末根可归属） |
| 双字根·三码全对齐 | 1819 | 27.4% | `xbk 禾x·口bk`（末根占两码） |
| 单字根（独占 / 四实例） | 251 | 3.8% | `Al 鹿Al` |
| 无法归属 | 182 | 2.7% | 退回纯编码 |

合计 **6435 字可显示**，占单字表 6640 的 96.9%。

样例：

```
的  d.O   →  d.O 白d·丶O
和  xbk   →  xbk 禾x·口bk
你  aLE   →  aLE 亻a·小E
德  ge:   →  ge: 彳g·心:
鸣  bXn   →  bXn 口b·鸟Xn
寒  jhS   →  jhS 宀j·冬字底S
鹿  Al    →  Al 鹿Al
```

## 4. 做不到的部分（诚实边界）

1. **多字根字的「第二根」名字缺失** —— 影响 65.8% 的字，注释里第 2 码只能无归属。要补齐必须重新导出 huma 的**全量**拆分序列（`elements.txt` 只导了首/末根），本仓没有 huma 本体，离线补不了。
2. **私用区（PUA）字根不可上屏** —— 首/末根引用里 **10.9%** 是 PUA 字（需 `zigen_table/ChaiPUA-0.2.7.ttf` 才显示），另有 4.1% 是笔画码 `1`–`6`。生成器已统一回退到 `mapping.yaml` 的中文描述（如「冬字底」「见字底」），笔画码映射为 一/丨/丿/丶/乛/乙。副作用是个别标签变长（3 字），注释宽度随之增加。
3. **2.7% 的字编码与取码规则不符** —— `yoyo-bm.dict.yaml` / `yoyo-pure.dict.yaml` 的码是 huma 为**降低重码**优化后的产物，不是纯函数。这类字宁可退回纯编码，也不猜。
4. **词不做拆分** —— 词全码 = 各字前两码，理论上可拆，但 4 字词会拼出 4 组「根+码」，候选窗口宽度不可接受；且反查里词的主码常是一简（如「可以」显示 `x`），信息量本来有限。

## 5. 落地内容

| 文件 | 作用 |
|---|---|
| `rime/scripts/gen_zigen_align.py` | 新增。反推字根码元 → 生成逐字拆分表；打印覆盖率与分歧 |
| `rime/lua/yoyo/data/zigen_align.lua` | 新增（生成物）。`字 → "全码 首根+首码·末根+末码"`，6435 条 / 196 KB |
| `rime/lua/yoyo/reverse_lookup.lua` | 改动。单字候选注释改用拆分表；`SHOW_ZIGEN` 一行开关；拆分表首次反查时懒加载 |
| `rime/scripts/test_reverse_zigen.lua` | 新增。stub 的 `Candidate/yield/log` 驱动真实翻译器，8 项断言 |

**注释语义变化**：改动前单字注释是「主码」，高频字多为**一简**（的 → `d`、和 → `x`）；改动后单字注释显示**全码 + 拆分**（的 → `d.O 白d·丶O`）。这是有意的：反查的目的就是学到完整打法。若要保留一简信息，可把注释格式再调（见 §6）。

回归：`lua5.4 test_reverse_zigen.lua` 8/8 通过；`lua5.4 test_brief_words.lua` 19/19 未受影响。

## 6. 取舍与备选

| 方案 | 优点 | 代价 |
|---|---|---|
| **A. 现方案**（全码 + 首末根，全部候选） | 一眼看到码位与字根对应 | 9 候选一页明显变宽 |
| B. 只标首根（`d.O 白…`） | 最窄 | 丢掉末根，价值下降一半 |
| C. 加 `switches` 开关（如 `zigen_hint`），默认关 | 不影响日常 | 要在 4 个 schema 各加一处 switch + filter 判断 |
| D. 词也拆 | 覆盖词 | 宽度不可接受 |

建议先按 A 用几天：注释变宽只在反查浮现时发生，不影响正常打字。若不适应，把 `reverse_lookup.lua` 顶部 `local SHOW_ZIGEN = true` 改成 `false` 即回到纯编码，无需重新部署数据。
